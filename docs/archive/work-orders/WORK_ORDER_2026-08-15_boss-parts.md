# 作業指示書 — ボスを部位分けし、レーザーを腕と噛み合わせる

作成日: 2026-08-15
状態: **完了（2026-08-16）。**`generate2dsprite` による単体素材生成、座標保持部位分割、腕連動レーザー、アンカー検証を実装済み。
対象: `nyabi-drone-core`（コース3のボス）

## 所長の決定（2026-08-15）

- **ボスの攻撃はレーザー多方向のみ。**急降下・吸引・結晶落としは採用しない
- **足場は既存のまま。**アリーナ（左右対称3段＋結晶成長装置）は変更しない
- **ボスは部位分けで作る。**本体は正面図のまま変えない

## 1. いまの問題（実測）

### (a) ボスだけ解像度が足りない

| | 素材 | 描画 | 倍率 |
|---|---|---|---|
| 雑魚ニャビドローン | 320×320 | 128×112 | 0.4倍 |
| **ボス** | **128×128**（中身84〜120px） | **430×390** | **約3.7倍に拡大** |

ボスは自分と同じドローンを召喚するので、**隣の雑魚のほうが精細**という絵になっている。

### (b) フレーム間で大きさと位置がズレる

`processed/` 実測。128px時点で幅26px・上端5pxのズレ = 430px描画では幅87px・縦17pxの跳ね。

| | 1 通常 | 2 予告 | 3 照準 | 4 被弾 |
|---|---|---|---|---|
| 中身の幅 | 109 | 109 | 120 | 94 |
| 上端 | 41 | 41 | 46 | 43 |

`processed-v2/` も同じ傾向（98 / 97 / 104 / 84）。**引き直しでは直らない。**

### (c) `main.js:1457` のマジックナンバー

```js
const spriteOpaqueTopOffset = boss.h * (41 / 128);
```

フレーム1の上端41を決め打ちしている。照準フレーム（上端46）に入るとボスが15px沈む。**絵を作り直すたびに当たり判定が黙ってズレる。**

### (d) 通常時に予告フレームを使っている

```js
: Math.floor(elapsed * 2) % 2   // 通常時、フレーム0と1を交互
```

フレーム1は予告（ビーコン発光）。**平常時からビーコンが点滅している**ので、本当の予告が読めない。

### (e) 腕の向きとビームの向きが無関係

ビームは `boss.x + 58` / `boss.x + w - 58`, `y + 195` の固定点から出る（`main.js:1467`）。腕がどこを向いていても同じ場所から水平に出るので、**腕を見ても着弾方向が分からない。**

レーザーが攻撃の全部を担う以上、これは致命的。**腕の向き＝予告**でなければならない。

## 2. 素材の作り方 — `$generate2dsprite` で1枚出し、別工程で切り分ける

**所長がChatGPTで作った参照画像をCodexのチャットに貼る。**それを参照として `$generate2dsprite` で本番素材を作る。ChatGPTの出力そのものは本番素材にしない。

### 生成

| 項目 | 値 |
|---|---|
| `asset_type` | `creature` |
| `view` | `side` |
| `bundle` | **`single_asset`** |
| `reference` | **`attached_image`**（所長がチャットに貼る） |
| `art_style` | `project-native` |
| `anchor` | `center` |

内容は**本体＋左右の前腕が基準姿勢（水平）で付いた正面図、ビーコン消灯**。任意で、同構図の**頭頂部の装甲が開いた版**をもう1枚。

### この素材で必ず守ること — 3つ

**(1) アニメーションシートにしない。1枚だけ出す。**

`$generate2dsprite` の処理系（`split_grid`）は、**セルごとに個別に bbox でクロップして再スケールする**。現行ボスの実測がその結果で、`shared_scale: true` を指定してもなお出力が 109×84 / 109×84 / 120×79 / 94×82 とバラついた。

**部位を別セルに置くと、本体と前腕の相対位置も縮尺も失われる。**肘の座標が意味を持たなくなるので、部位分けが成立しない。本体と両腕は**同じ1枚の中**に置くこと。

**(2) `cell_size` に 128 を使わない。**

現行ボスは `cell_size: 128` で処理され、それを 430×390 に拡大して描いている。これが解像度不足の原因。**出力の短辺で最低768px**を確保する。

**(3) 正方形セルに押し込まない。**

腕が左右へ大きく張り出すので bbox は横長になる。固定正方形セルに入れると**本体がその中で縮む**（スキル自身が「wide bbox は body を縮ませる」と警告している）。単一アセットとして、横長のまま出す。

### 後処理でやること／やらないこと

- **やる**: マゼンタ `#FF00FF` 抜き、輪郭のクリーンアップ、余白トリム
- **やらない**: セル分割、フレームごとの個別リスケール、正方形への正規化

### 切り分けは別の決定的スクリプトで

`tools/split_boss_parts.py` を新設し、`$generate2dsprite` の出力1枚から座標を保ったまま切り出す。

| 部品 | 内容 |
|---|---|
| `body` | 前腕を除いた本体。**肩アーマーと上腕は本体に含める**（動かないので） |
| `forearm` | 右の前腕＋砲口。**左は反転して使う**（左右で描き分けない） |
| `beacon-exposed` | 装甲が開いた版の頭頂部だけ（任意） |

**切断位置は、胴体にいちばん近い球関節。**採用参照画像は球関節が片腕に2〜3個並ぶが、内側で切ると回転部品が長くなって向きが読みやすく、かつ切り口が胴体のシルエットに掛からない。

切り出した各部品は**元画像の座標系での位置を保持**し、そのまま `anchors` に記録する。部品を個別にトリムして原点情報を捨てない。

**スラスターの噴射・ビーコンの発光・被弾フラッシュは生成しない。**コードで描く（`ctx.shadowColor` で既に実装がある）。

### アンカーを `pipeline-meta.json` へ書き出す

**マジックナンバーを二度と作らないために、絵と当たり判定の対応をデータで持つ。**単位は本体画像のピクセル、原点は本体画像の左上。

```json
"anchors": {
  "bodyTopOpaque":  { "y": 41 },
  "weakPoint":      { "x": 215, "y": 8,   "w": 110, "h": 62 },
  "elbowLeft":      { "x": 92,  "y": 205 },
  "elbowRight":     { "x": 338, "y": 205 },
  "muzzleFromElbow":{ "dx": 96, "dy": 14 },
  "forearmAngleLimit": { "min": -60, "max": 60 }
}
```

- `weakPoint` は現行の頭の当たり判定（`boss.x + 160, boss.y - 12, 110×62`）と一致させる
- `elbow*` が前腕の回転中心。**採用素材は球関節が片腕に2〜3個並ぶので、胴体にいちばん近い球を肘とする。**回転部品が長くなって向きが読みやすく、かつ切り口が胴体のシルエットに掛からない
- `muzzleFromElbow` は**肘から砲口への2次元ベクトル**。採用素材の前腕は完全な水平ではないので、距離だけでは足りない。基準角は `atan2(dy, dx)` で求め、コードはそこからの差分だけ回す
- `forearmAngleLimit` は基準角からの可動範囲。**肘が胴体の外側にあるため、上へ振りすぎると耳に被る。**±60度に収める。フェーズ3の回転薙ぎもこの範囲の往復で作る
- **`main.js` は `41/128` をやめ、`anchors` を読む**

## 3. 描画の作り直し（`main.js:1454`〜）

1. 本体を描く（1枚のみ。フレーム切替をやめる）
2. **左右の前腕を、それぞれの肘を中心に回転して描く**
3. ビームは**砲口の位置から、前腕と同じ角度で**出す
4. ビーコンの発光・被弾フラッシュ・スラスターはコードで重ねる

### 状態と見た目の対応

| 状態 | 前腕 | ビーコン |
|---|---|---|
| 通常 | 水平で待機。ゆっくり上下 | **消灯** |
| 予告 | **次に撃つ角度へ向く**（発射前に向き切る） | 点滅 |
| 発射 | その角度のまま | 点灯 |
| 隙 | だらんと下がる | 露出（B があれば差し替え） |
| 被弾 | 跳ね上がる | 白フラッシュ |

**予告の本体は「前腕が向きを変えること」。**ビーコンはタイミングを伝えるだけ。

## 4. レーザーの仕様

アリーナは左右対称3段（`bossArenaLayout`: `groundY 1274` / `firstFloorRise 320` / `tierRise 244`）で、HP3段階と高さが対応している。**高さが変わると同じレーザーの意味が変わる**ので、それを使う。

| HP | ボスの高さ | レーザー | プレイヤーがすること |
|---|---|---|---|
| **3** | 1段目 | 水平の薙ぎ。**低い（床すれすれ）と高い（腰の高さ）を撃ち分ける**。左右の腕が別々に | 予告線の高さを見て、跳ぶか滑るか即断 |
| **2** | 2段目 | **斜め下**へ。左右の腕から同時にV字 | 下の段に留まれない。真下が安全地帯 |
| **1** | 3段目 | **回転薙ぎ**（1本をゆっくり回す）＋扇状の同時発射 | 崩れる結晶足場の上で通過の隙間を読む |

- 低い薙ぎは**スライドでは避けられない高さ**、高い薙ぎは**ジャンプでは避けられない高さ**にする。どちらか一方の動詞しか通らないこと
- 撃ち分けは腕の角度だけで作る。新しい絵は要らない
- 発射後の硬直が**唯一の攻撃機会**。ここを十分長く取る

### 守るルール

**予告は同時に1つだけ。**扇や2本同時は「1つの予告で複数の線」として出す。別々の予告を重ねない。この作品は「予告→発動」を危険の文法にしている（`docs/FLOOR_DESIGN.md`）ので、そこが崩れると理不尽になる。

## 5. 検収条件

- ボスの素材が **860px以上**（430×390描画で拡大にならないこと）。`cell_size: 128` の処理を通していないこと
- 本体と前腕が**同じ1枚の生成物から**切り出されており、`anchors` の座標が元画像の座標系で一貫していること
- **どの状態でもボスの本体が縦横に跳ねない**（フレーム切替をやめたので構造的に起きないはず）
- `main.js` に `41/128` のようなマジックナンバーが無く、`anchors` を読んでいる
- **腕が向いている方向にビームが出る**。全角度で一致すること
- **通常時にビーコンが光らない**
- 低い薙ぎはジャンプで避けられ、スライドでは当たる。高い薙ぎはその逆
- 予告が2つ同時に出ない
- `npm run validate` と `npm run build` が通る

## 6. 守ること

- **本体は正面図のまま。**見た目を変えない
- 左右の前腕を描き分けない（反転で使う）
- 見た目の良し悪しを自動検査しない。検査するのは `anchors` の有無・参照・寸法など静かに壊れるもの
- 新しい可視アセットは所長が採用してから作る
