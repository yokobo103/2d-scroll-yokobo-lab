# 作業指示書 — 舞台装置のシルエット一覧をスプライトの前に置く

発行日: 2026-08-14
対象: `20260810_ニャビットの暴走実験室`
前提資料: `docs/FLOOR_DESIGN.md`、`docs/archive/work-orders/WORK_ORDER_2026-08-13.md`（カタログ方式。**破棄しない。工程を1つ手前に足す**）

## 0. 何が足りなかったか

`WORK_ORDER_2026-08-13.md` でカタログ方式を入れたが、**カタログに載る前の工程が無かった**。所長の指摘はこうである。

> 使用する全ての舞台装置をみて、これとこれはなんか違う、ってやりたい。もちろんスプライトシート作成する前段階で。
> 挙げてくれたやつは大きめのギミック装置としてはありだけど、繰り返しでてくる妨害装置としてはデカすぎて、どう避けたらいいのかわからん。
> 細かいところより先にフォルムをみたい。

現行カタログは「完成したスプライトを1種別ずつ」見せていた。決めるべきなのはその前段階、**フロア全体の顔ぶれと、それぞれの大きさとフォルム**である。

プレイヤー: 判定 92×142 / **描画 194×194**

|---|---|---|---|

| `spill-01` | **210×94** | 166×62 | プレイヤーより横に広い |

| 敵4体 | 描画 156〜202 | — | 全部ほぼ同じ大きさ |

3つの問題が同時に見える。

1. **繰り返し出る妨害装置がプレイヤーと同大。**跳ぶのか滑るのか、絵が答えを出していない
2. **絵と危険範囲が一致していない。**噴出口は絵の3分の1しか当たらない。「どう避けたらいいのかわからん」は正確な感想であり、**絵が嘘をついている**
3. **サイズに階層が無い。**全部が90〜280に固まっていて、大きさで「大事なもの／背景」を区別できない。看板が一番大きいのはその結果

**2と3は、1種別ずつ見ていては絶対に気づけない。**全部を同じ縮尺で並べて初めて出る。

## 1. 足す工程

```
【新設】フロア舞台装置のシルエット一覧   ← フォルムと大きさをここで決める
   ↓ 採否（「これとこれは違う」）
   ↓ 決まったフォルムだけ
スプライト生成（generate2dsprite）
   ↓
カタログ候補シート（WORK_ORDER_2026-08-13.md の仕組み）
   ↓ 採否
フロア正本
```

シルエット段階は**生成を使わない。**コードで描く。理由は3つ。

- 速い。数秒で描き直せるので、その場で何度も振れる
- 形を意図して振れる。生成ガチャだと大きさも形も揃わない
- **精密でないほうが目的に合う。**色とディテールが無いほうがフォルムだけ見られる

## 2. サイズクラスを共通語彙にする

大きさは感覚ではなく**役割から決める**。プレイヤー描画194を基準にする。

| クラス | 役割 | 目安 | 該当 |
|---|---|---|---|
| **L 舞台装置** | ステージに1〜2個。目印になる | 250〜400 | 出口リフト、巨大コア |
| **M 操作ギミック** | 区間に1個。触る・押す対象 | 140〜200 | 起動スイッチ、チェックポイント、昇降リフト |
| **S 妨害装置** | **繰り返し出る。避け方が一目で読める必要がある** | **70〜110** | **噴出口、液だまり** |
| **XS 収集・小物** | 散在する | 60〜90 | 結晶、コイン、アイテム |
| **敵** | 動く障害 | 120〜180 | ニャビクリーン、ネジニャビ、ニャビドローン |
| **掲示** | 情報。**主役ではない** | 100以下、または中景で小さく | 案内・注意・チュートリアル |

**Sクラスの原則: プレイヤーの半分以下。**跳ぶか滑るかが、大きさだけで分かること。

`data/asset-catalog.json` の各エントリに `sizeClass` を足す。

## 3. 絵と危険範囲を一致させる

**外形＝危険範囲**を原則にする。inset で誤魔化さない。

- 噴出口なら、**噴出している柱そのものを絵の主体**にする。台座は小さく、危険範囲の外に出さない
- どうしても絵が危険範囲より大きくなる場合は、**危険でない部分を中景層へ分離する**（台座だけ別Prefabにする等）

現行 `energy-vent-v1` は描画180幅／危険64幅。これは分離の対象である。

## 4. やること

### T1. シルエット抽出＋描画ツール

`tools/build_floor_silhouette_sheet.py` を新設する。

**既存アセット**は runtime PNG の**アルファチャンネルから塗りつぶしシルエット**を作る。新規案は**幾何図形の組み合わせでコードから描く**。両方を同じシートに載せて比較できるようにする。

シートの要件:

1. **1Fで使う舞台装置を全部載せる。**足場・装置・妨害装置・収集物・敵・掲示・ギミック・出口。**1種別だけにしない**
2. **全部を同じ縮尺**（ゲーム内の描画サイズ）で並べる
3. **Dr.よこぼのシルエットを、各カードに定規として必ず入れる。**大きさの比較はこれが無いと成立しない
4. **サイズクラスごとに行を分ける**（L / M / S / XS / 敵 / 掲示）
5. **単色の塗りつぶし。**色・ディテール・輪郭の描き分けをしない。フォルムと大きさだけを見る
6. **通し番号を振る**（採否を番号で言うため）
7. 危険判定を持つものは、**危険範囲を細い枠で重ねて表示**する。絵と判定のズレが見えるように
8. PC幅と390px幅の両方

出力: `screenshots/silhouette-<floor>-all.png` と `-mobile.png`

### T2. Sクラスの新案を出す

現行の噴出口・液だまりは大きすぎる。**Sクラス（70〜110）に収まる新しいフォルム案を、噴出口だけで4〜6案**シルエットで描く。

案を振る軸は**フォルム**であって、色でも輪郭でもない。例:

- 床から短く噴く縦長の口
- 床に埋まった円形の口（噴出時だけ縦に伸びる）
- 壁付きで横に噴く口
- パイプの破断部（横長・低い）

**生成しない。**コードで描いた図形で足りる。

### T3. 台帳にサイズクラスを足す

`data/asset-catalog.json` の各エントリに `sizeClass`（`L`/`M`/`S`/`XS`/`enemy`/`sign`）と `silhouette`（シルエット画像のパス）を足す。

`tools/validate_catalog.mjs` に検査を1つだけ追加する。

- **`data/*.json` が参照する可視アセットの描画サイズが、その `sizeClass` の範囲に収まっていること**

これは静かに壊れる（数字なので画面を見ても気づけない）ので検査に値する。**見た目の良し悪しは引き続き検査しない。**

### T4. 掲示を小さくする

`area-guide-panel-01`(280×180) / `tutorial-panel-01`(260×180) / `caution-panel-01`(240×170) は、画面内で最大の物体になっている。サイズクラス「掲示」に合わせて縮める案をシルエットで出す。

**ただし縮めると文字が読めなくなる**ので、シルエット段階では大きさだけ決め、可読性は次段階（スプライト生成時）で解く。案としては「小さい看板＋近づくとトースト表示」がある。

### T5. 一覧を「台本」にする — 効果と設定を並べる

所長の要件: **全アセットを、効果と設定込みで見て、フロアのイメージに合わないものを除外したい。**

調査の結果、3要素のうち2つは既にデータにある。**足りないのは「設定」だけである。**

| 要素 | 状態 |
|---|---|
| フォルム・大きさ | 既存の runtime PNG と描画サイズ |
| **効果**（ゲーム上何をするか） | `presentation` / `collision` / `itemEffect` / `behavior` にすべて存在。出現数も配置から計算可能 |
| **設定**（世界観上これが何なのか） | **26 Prefab中 26個が未定義** |

この欠落が、これまでの見た目のズレの根本原因である。生成時に渡せる情報が `hazard` / `damage` しかなく、**「これが何なのか」を一度も決めていなかった。**設定が1行あれば、生成プロンプトは自動的に研究所の設備になる。

#### 5-1. Prefabに `lore` を追加する

`data/prefab-registry.json` の各Prefabに `lore`（1〜2文）を追加する。**§5-4 の原案をそのまま初期値として入れる。**

#### 5-2. 効果の列は自動生成する

手書きしない。次から日本語1行を組み立てる。

- `collision.factory` → `oneWayRect`＝乗れる / `hazardRect`＝常時ダメージ / `timedHazardRect`＝周期ダメージ / `sensorCircle`＝取得 / `enemyRect`＝接触ダメージ・踏める / `sensorRect`＝作動
- `collision.damage`、`collision.radius`、`collision.width×height`（**危険範囲**）
- `itemEffect.type` / `value`
- `behavior.preset` / `interval`、周期ハザードの `period`
- 配置データから数えた**出現数**

例: `energy-vent-v1` →「周期3.4秒で噴出。作動中に触れて1ダメージ。危険範囲 64×174 / 出現2」

#### 5-3. 除外候補を自動でフラグする

次に当てはまるものへ、シート上に **除外候補** の印を出す。判断は所長が行うが、**構造的に怪しいものは機械が指摘する。**

- **出現数0**（配置されていないのに登録だけ残っている）
- `gameplaySignal: "none"`（効果を持たない）

現時点の該当:

| Prefab | 理由 |
|---|---|
| `slime-robot-v1` | 出現数0。初期の試作敵の残骸。画像4枚が `dist` に同梱されたまま |

| `lab-bottle-rack-v1` / `lab-wall-panel-v1` / `lab-cable-coil-v1` | `gameplaySignal: none` |

#### 5-6. 採否の粒度

所長の返答は3種類を受け付ける。

- **採用** — このまま使う
- **除外** — フロアのイメージに合わない。配置とPrefabを消す
- **作り直し** — 役割は要るが、フォルムか大きさが合わない

`tools/apply_catalog_decision.mjs` をこの3値に対応させる。理由は `docs/floors/1f/CANON.md` の「避けること」へ追記する。
